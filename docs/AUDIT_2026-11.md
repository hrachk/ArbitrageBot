# Аудит ArbitrageBot (ветка Live-Branch-1), 2026-11-18

## Главный вывод

Paper-результат (+$96 по 153 закрытым сделкам при notional ≈ $480) **нельзя считать доказательством edge**.
Paper исполнял сделку мгновенно по ценам того же стакана, который дал сигнал. Значимая часть прибыли
пришлась на сделки, которые «сошлись» за доли секунды. Это классический фантомный арбитраж:
одна котировка устарела, «спред» — это задержка, а в live он исчезает раньше, чем дойдёт ордер.

Данные из `data/paper/trades-ledger.json`:

| Время удержания | Сделок | PnL, $ |
|---|---|---|
| ≤ 1 с | 20 | +20.97 |
| ≤ 30 с | 79 | +74.72 |
| > 120 с | 40 | +1.43 |

- Входы со спредом 0.5–1% закрывались в среднем за **0.8 с**.
- Сделки, удержанные дольше 2 минут, дали в сумме почти ноль.

Эти правки делают paper честным. Теперь он моделирует задержку, IOC-лимиты, промах одной ноги,
устаревшие котировки и глубину на выходе. **Прибыльность нужно заново подтвердить на новом paper**,
прежде чем включать live.

## Найденные ошибки и исправления

| # | Проблема | Последствие | Исправление |
|---|---|---|---|
| 1 | `RequiredNetPercent` молча снижал порог оператора до 0.04% (сохранённый 0.12 → 0.04) | Бот торговал в 3 раза более тонкий edge, чем задано | Пол 0.02%, без верхнего клампа (`ArbEconomics`) |
| 2 | `RequiredTakeProfitUsd` срезал $0.50 до ~$0.10 на $100 | То же самое, по доллару | Берётся максимум из настройки и пола |
| 3 | `MinGrossSpreadPercent` обрезался до 0.22 (настройка 0.40) | Порог gross игнорировался | `RequiredGrossPercent`, без верхнего клампа |
| 4 | Persist зажат в 200–500 мс (настройка 800) | Настройка игнорировалась | 200–5000 мс |
| 5 | Fair basis считался «готовым» через 12 с и 4 точки; EMA с seed первой точки | Basis ≈ один случайный тик, excess = шум | `BasisEstimator`: ≥60 точек и ≥90 с, отсев выбросов (спайк не учит базис) |
| 6 | Свежесть котировок: пол 1500 мс для WS, REST-котировки до 4 с участвовали как торгуемая нога | Главный источник фантомных спредов | `QuoteGate`: нога ≤ 1000 мс, расхождение ног ≤ 600 мс, REST никогда не торгуемая нога; базис учится только на свежих ногах |
| 7 | Paper исполнял мгновенно по цене сигнала | Фантомная прибыль | Ордер «прибывает» через `PaperFillLatencyMs` (250 мс), IOC-лимит ±`IocSlipBps`; промах одной ноги стоит 2 комиссии + ширину стакана, как в live |
| 8 | Метки выхода по top-of-book | Завышенный выход для любого размера | Выход проходит по глубине на объём позиции (`ExitMarks`) |
| 9 | Orphan-закрытие по возрасту позиции: один пропущенный тик после 3 мин закрывал хедж с убытком и баном на 6 ч | Ложные убытки и баны | 3 минуты **непрерывного** отсутствия котировки (`NoMarkSinceUtc`) |
| 10 | На выходе комиссия по умолчанию 0.05% вместо таблицы (KuCoin/Bitget 0.06%) | Занижение комиссий в paper | Везде `ArbEconomics.TakerPercent` |
| 11 | `RefreshFundingCacheAsync` вызывался с `await` внутри скана (350 мс сна на символ) | Цикл замирал на секунды, книги старели | Фоновая задача |
| 12 | Funding: последняя **исторически выплаченная** ставка, фиксированные периоды; для Bitget/Gate/KuCoin funding = 0 | Gate funding почти слепой | `FundingModel`: учитываются только расчёты каждой биржи, попадающие в горизонт удержания, по текущей ставке; неизвестная ставка в горизонте = вето |
| 13 | Live: LONG → ожидание подтверждения → SHORT | Хедж висел на одной ноге всё время REST-круга; короткий IOC часто промахивался → unwind | Обе ноги уходят одновременно (`LiveConcurrentLegs`), безопасный unwind/карантин для любой комбинации исходов |
| 14 | IOC slip в live захардкожен (4 bps) | Paper и live могли разойтись | Общая настройка `IocSlipBps` |
| 15 | `RuntimeRiskConfig.Snapshot` клонировал все опции при каждом чтении (много раз на пару за скан) | Тысячи аллокаций в секунду | Кэш, инвалидация при изменении |

## Новые настройки (секция `Arbitrage`)

| Ключ | Дефолт | Смысл |
|---|---|---|
| `TradeMaxQuoteAgeMs` | 1000 | Макс. возраст котировки торгуемой ноги |
| `MaxLegSkewMs` | 600 | Макс. разница возраста двух ног |
| `BasisMinSamples` / `BasisMinSpanSeconds` | 60 / 90 | Прогрев fair basis |
| `PaperFillLatencyMs` | 250 | Задержка исполнения в paper |
| `IocSlipBps` | 4 | Запас IOC-лимита (paper и live) |
| `FundingHorizonMinutes` | 20 | Горизонт, в котором funding списывается с edge |
| `LiveConcurrentLegs` | true | Одновременная отправка ног |

## Тесты

`dotnet run --project ArbitrageBot.Tests` — 51 тест без внешних пакетов. Покрывают:

- экономику и регрессии клампов;
- тождество «прогноз revert-PnL в скане = фактический PnL выхода в paper»;

- глубину стакана.

## Операционные риски, которые нужно закрыть вручную

1. **`data/` и `data/local-settings.json` отслеживаются git**, несмотря на `.gitignore`.
   - Если положить ключи в `local-settings.json`, `git commit -a` отправит их в репозиторий.
   - Сначала сделайте резервную копию `ArbitrageBot/data/`, затем выполните `git rm -r --cached ArbitrageBot/data` и закоммитьте.
2. В репозитории лежат ~48 МБ логов событий paper. После шага 1 они уйдут из индекса.
3. Комиссии в таблице соответствуют уровню VIP0. Если есть скидки, укажите реальные значения в `EstimatedTakerFees`.

## Порядок запуска

1. `dotnet build` и `dotnet run --project ArbitrageBot.Tests` локально.
2. Paper минимум 5–7 дней с новыми настройками. Смотрите:
   - долю `ioc-miss` и `Closed(leg-miss)`;
   - PnL по времени удержания;
   - PnL на сделку после промахов.
3. Live только если paper положителен **после** промахов ног.
   - Начинайте с read-only и сверки балансов.
   - Затем $100 на биржу, 1–2 символа, `FuturesMaxOpenPositions = 1`.
4. Каждую неделю сравнивайте live-fill с paper-fill. Если live систематически хуже, увеличьте `PaperFillLatencyMs` до измеренной реальной задержки.
